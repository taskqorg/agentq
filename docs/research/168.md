# Research 168: PilotQ dynamic-tool result sizes

## Question

Do PilotQ's Codex dynamic tools return results large enough to justify the agentq compression adapter proposed in [#167](https://github.com/taskqorg/agentq/issues/167)? The owner chose "measure first" on #167. On 2026-10-29 the owner directed this task to use the data available now: the [pilotq#42](https://github.com/taskqorg/pilotq/issues/42) trial export and the [pilotq#40](https://github.com/taskqorg/pilotq/issues/40) automatic suite. No further pilot window is waited for.

## Findings

### Logging exists (acceptance A1)

[pilotq#31](https://github.com/taskqorg/pilotq/issues/31) added the size record. Each dynamic-tool call writes one `tool_sizes` row: tool name, UTF-8 result bytes after key scrubbing, Codex version and pilotq version, and no result content (`src/journal.rs` `tool_size`, called from `src/manager.rs` for every tool call). `pilot report --json` adds a `tools` array with `calls`, `p95_result_bytes` (nearest rank) and `max_result_bytes` per tool. The report omits the per-row versions. All references are to pilotq main at [`139a3c4`](https://github.com/taskqorg/pilotq/tree/139a3c4a4035c52e13dd8612078c220699971ce6) (version 0.2.12).

### Size bounds from the code

These bounds are code-derived ceilings, not measurements. "Fixed text" means the constant wording around variable values.

| Tool | Result shape | Upper bound |
|---|---|---|
| `task_plan` | Fixed text (about 240 B) and up to 3 ticket titles of at most 80 characters | about 0.5 KB for ASCII titles; 1.2 KB worst case for 4-byte characters |
| `task_run_plan` | One fixed sentence | about 0.2 KB |
| `task_status` | Header, one line per attempt with its reason, open question card | Not bounded by code; grows with the attempt count |
| `project_list` | Complete JSON of accessible projects | About 0.1 KB per project; 2 projects in the trial |
| `project_use` | One sentence | about 0.1 KB |
| `issue_read` | Header (about 215 B), the issue title (GitHub allows 256 characters) and a body excerpt of at most 1500 characters | about 2.0 KB for ASCII; 7.2 KB worst case for 4-byte characters |
| `issue_comment` | Write receipt with URL and operation ID | about 0.3 KB |
| `project_status` (0 calls) | Complete JSON of all board tasks | Not bounded by code |
| `command_run` (0 calls) | Complete JSON; stdout and stderr capped at 16 KiB together | about 16.5 KB |

PilotQ also limits each request to 5 tool calls (`direct::BUDGET`).

### What agentq would do with these results

Under agentq.md § 3, the compression core:

- passes results under `min_bytes` (default 2048) with reason `short`;
- passes complete JSON with reason `json` (PRODUCT R3), which covers `project_list`, `project_status` and `command_run`;
- selects an engine only from the built-in RTK runner list (`pytest`, `cargo test|build|check`, `go test`). PilotQ dynamic tools run no runner, so every other result passes as `not_qualified`.

Six of the seven measured tools have a code ceiling below 2048 bytes for ASCII text; `issue_read` reaches about 2.0 KB only with a maximum-length title and body. `task_status` is the only measured tool whose size can grow past that without bound. Its text is a short list of task attempts and reasons, which has no qualified engine. A #167 adapter therefore needs a § 3 decision change (a new text engine) before it could compress anything. The trial shows no measured result that would justify that change.

## Options

1. **Close #167 as not needed.**
   - Pro: no § 3 decision change or new engine; matches the code ceilings and the owner's direction to close on current data.
   - Con: p95 and max bytes stay unmeasured; a later large `task_status` or a new PilotQ tool would need a new task.
2. **Keep #167 parked until the PM posts the size section.** The PM runs `pilotq pilot report --json` on pds18 for the trial window and posts its `tools` array.
   - Pro: measured p95 and max per tool, which completes A2 exactly.
   - Con: another wait on a host step; the code ceilings already show the result for six of seven tools.
3. **Reopen #167 for `task_status` and `issue_read`.**
   - Pro: covers the only tools that can exceed 2 KB.
   - Con: needs a § 3 change and a new text engine for results that are mostly below `min_bytes`; no measurement supports it.

## Recommendation

Option 1: close #167 as not needed. The code bounds every measured tool except `task_status`, and no qualified engine applies to any of them. Reopen #167 only when a PilotQ size report shows a tool with p95 above 2048 bytes.

## Decision

The owner chose option 1 on [#168](https://github.com/taskqorg/agentq/issues/168) (answer 6508437462): close #167 as not needed. agentq.md § 3 stays unchanged. The p95 and max bytes stay unmeasured; reopening #167 needs a new size readout.
