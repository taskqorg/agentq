# Research 253: PilotQ Codex app-server framing failure

## Question

Why did PilotQ 0.2.43 manager requests 714 and 716 fail before any tool at 2026-11-06 00:25 and 00:29 UTC with `Codex CLI exited without a terminal event`, while PID 451080 logged `app-server record incomplete or exceeds 8 MiB` twice? Which bounded recovery keeps the native history and effect receipts?

## Findings

Short answer: the deployed PilotQ binary is bound to its release and runtime pin. The cause of requests 714 and 716 stays inconclusive: their failure text covers both causes, and no retained metadata records the frame size. The leading hypothesis is that PilotQ resumes a long thread with its full history in one reply over the 8 MiB per-record bound, so the runtime stops the server before any input. That mechanism is reproduced offline on real Codex, and it is not proved for these two requests.

### A1: request trace, from released source

This worker read PilotQ source at tag `v0.2.43` and did not read the host journal or the request records. The times, the PID and the two messages come from the task text. The PM also reports the next scheduled failure at 00:39 UTC in Telegram (task comment 6673559759).

1. `src/manager.rs:319` runs `a.resume(s, &l)` or `a.launch(&l)` on a launch thread. The app-server handshake happens inside that call, before `a.input`.
2. A launch failure reaches `src/manager.rs:337`, the only `host::log` site that logs a manager launch error, under the runtime name.
3. `src/manager.rs:338` then replies `{label} exited without a terminal event`, because the child had already spawned (`LaunchFailure::Exited`).

Together, the journal line and the reply place both failures in this launch path. A failure after launch would reply differently: a read error during the turn returns its own text from `src/manager.rs:442`. No `turn/start` follows a failed handshake, so no tool ran, which matches "failed before tools". Codex did not necessarily exit. The handshake failure makes the runtime kill the child, so the reply label can mislead.

| Release binary | `pilotq-0.2.43-linux-x86_64` has the same full SHA-256, re-hashed here and equal to the release `SHA256SUMS`. It embeds the path segment `33cef65`, holds the exact error string once and never holds `excludeTurns`. |

The process that logged both messages therefore runs the released artifact, byte for byte. The runtime revision follows from the tag's `Cargo.lock`, the embedded `33cef65` segment and the error string in that artifact. No reproducible rebuild was attempted, so this is strong artifact evidence and not a build proof. The hash was read after the failures, while PID 451080 was still the same process.

### A2: incomplete EOF against frame size

The pinned reader joined two different causes into one message, so the journal text alone cannot separate them. It decoded before it checked the size, so an oversized frame with a multi-byte character across the bound logs `app-server read failed: stream did not contain valid UTF-8` instead. The journal shows the shared message, so a size failure would have needed its first 8 MiB + 1 bytes to be valid UTF-8. That does not separate the causes either. Each native record is a single stdout line. `thread/resume` returns `thread.turns` unless the caller excludes it, and PilotQ does not exclude it.

Measured with `docs/research/253-resume-frame.py`, real `codex-cli 0.162.0` (the documented minimum), macOS arm64, an isolated home, an invented rollout and a loopback mock provider:

| Rollout | `excludeTurns` | `thread/resume` frame | Turns in reply | Over 8 MiB | `thread/turns/list` page (5 turns) |
|---|---|---:|---:|---|---:|
| 2,132,244 B | no | 1,065,776 B | 40 | no | 133,173 B |
| 2,132,244 B | yes | 1,766 B | 0 | no | 133,173 B |
| 25,200,884 B | no | 12,600,096 B | 40 | **yes** | 1,574,963 B |
| 25,200,884 B | yes | 1,766 B | 0 | no | 1,574,963 B |

`codex-cli 0.159.3` gave the same result with a 12,599,519 B frame without the flag and 1,749 B with it. The ratio of frame to rollout is about 0.5 here, on text-only fixtures. Real rollouts hold other record types, so a rollout size alone predicts the frame only roughly.

Inference, not observation, favors frame size over EOF:

- The size failure is deterministic and repeats at the same protocol step until the history shrinks, which never happens. EOF would need the native server to die inside a record each time at the same step.
- A long manager thread is exactly the case that grows without limit, and resume is the only handshake reply carrying history.

**Requests 714 and 716 stay inconclusive between size and EOF.** The reader discards the bytes and logs no count, and PilotQ writes only non-JSON stdout lines to its private log, so no retained metadata records these frames. Later evidence does not close this:

- A future error with the split messages describes that later attempt, not these two requests.
- A rollout size predicts a frame only roughly, because real rollouts hold other record types.

### A2: resume reply and caller use

Neither reader of the reply needs the turns:

- `AppSession::observe_inner` reads only `result.thread.id` and `result.model`.
- PilotQ `v0.2.43` source has no read of `turns` at all. Its history for recovery comes from its own journal.

`thread/resume` with `excludeTurns: true` keeps the model context. Same fixture, 20 synthetic turns, one mock model request per case:

| `excludeTurns` | Resume frame | Turn status | Model request bytes | Input items | History markers |
|---|---:|---|---:|---:|---:|
| no | 91,396 B | completed | 128,337 | 44 | 21 |
| yes | 1,766 B | completed | 128,337 | 44 | 21 |

The request body has the same size and the same counts in both cases. Paged history stays readable through `thread/turns/list`.

Native `thread/resume` appends to the rollout by itself (809 B per resume at 0.162.0), with or without the flag. The earlier bytes stay byte-identical. So each failed attempt in production most likely added a small native record. This is native behavior and not a history edit by AgentQ or PilotQ.

### A3: reproduction and before/after

Fixtures are invented and bounded. Output is counts, sizes and native error codes only.

- Native frame: the table above, by `docs/research/253-resume-frame.py`.
- Reader: `app_resume_frames_stay_bounded_and_named` in `runtime/tests/agent.rs` drives the runtime against a fake app-server with four replies: `native` (over the bound unless excluded), `exact` (exactly 8 MiB, accepted), `over` (8 MiB + 1 byte) and `cut` (stream ends inside a record).
- Before this change the test fails: `over: app-server record incomplete or exceeds 8 MiB`.
- After the split the test passes, with `app-server record exceeds 8 MiB; native state unknown` and `app-server stream ended inside a record after <n> bytes; native state unknown`. The message carries a count and no record content. No `turn/start` follows either failure.
- Review of the split found a second defect, kept in the same test. `over-utf8` is valid JSON with a two-byte character across the bound. Before the byte-first reader it fails: `over-utf8: app-server read failed: stream did not contain valid UTF-8`. After it, the frame reads as size.
- The reader now checks bytes before decoding. `exact-utf8` keeps a valid record of exactly 8 MiB, `cut-utf8` reads a stream cut inside a character as an ended stream, and `invalid` reads a complete non-UTF-8 record as `app-server record invalid; native state unknown`.

### Related hazard found: any resume refusal reads as a missing session

The app session drops the native error text and returns `app-server thread/resume refused; original session retained`. `launch_refusal` maps that string to `session-missing`, at the pin and on main. PilotQ then rebuilds from its journal on a **new** native session (`src/manager.rs:261`, `:334`).

The fixture shows both refusals use the same code and different messages:

| Case | Code | Message |
|---|---:|---|
| Thread absent | -32600 | `no rollout found for thread id <thread>` |
| Second writer | -32600 | `thread <thread> already has an active writer` |

So a busy thread can replace the native session, although the thread still exists. This did not cause requests 714 and 716, because their failure is a framing error, not a refusal. It does threaten the native session this task must preserve.

## Options

**1. PilotQ sends `excludeTurns: true` on resume (recommended, recorded as [pilotq#390](https://github.com/taskqorg/pilotq/issues/390)).** One line in the resume branch at `src/manager.rs:304`.
- Pros: removes the cause at its source and needs no runtime bump, because the pinned runtime passes caller parameters unchanged. Keeps thread ID, model context, login, grants and history.
- Cons: needs a PilotQ release and PM qualification. A single oversized live notification would still fail its turn with a named error.

**2. Raise the record bound.**
- Pros: no caller change.
- Cons: only delays the failure, because history keeps growing. Every reply is held in memory, and an unbounded raise is forbidden by A4.

**3. AgentQ adds `excludeTurns` for every resume in `Mode::AppServer`.**
- Pros: covers all callers.
- Cons: alters the documented rule that caller thread parameters pass unchanged, so it is a decision change. PilotQ also needs a runtime bump across the #249 interface change.

**4. Start a new native thread, or trim the rollout.**
- Pros: frees the session at once.
- Cons: a new thread loses native continuity and trimming edits history. A4 forbids both.

**5. Paid API fallback or replay.** Forbidden by A4 and not considered further.

## Verdict

Inconclusive for the two live requests, confirmed for the mechanism. The deployed binary is bound to the release by its full hash. Real Codex produces a resume frame over the 8 MiB bound, the pinned runtime refuses it before input, and `excludeTurns` brings it to under 2 KiB with an identical model request. Size against EOF for requests 714 and 716 stays blocked on evidence that no retained record holds.

## Recommendation

Send `excludeTurns: true` on PilotQ resume through [pilotq#390](https://github.com/taskqorg/pilotq/issues/390), release it, and have the PM qualify a real manager turn on the same native thread. If that turn succeeds, it shows recovery and still does not name the cause of requests 714 and 716. Do not raise the bound, start a new thread, or edit the rollout. Keep the existing native session and the journal as they are until then. The failed attempts submitted no input, so they need no replay. This change also ships the byte-first reader and split messages in AgentQ, so a later framing failure names its own cause once PilotQ picks up a newer runtime. PilotQ 387 continues independently.
