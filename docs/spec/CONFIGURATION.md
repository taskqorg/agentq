# Client integration configuration

Accepted target under agentq.md §§ 4/6/8 and PRODUCT R1–R5/R7/R9. Extends [enrollment](ENROLLMENT.md) with separately authorized typed configuration; observation enrollment remains unchanged. DashQ owns the [consumer interface](https://github.com/taskqorg/dashq/blob/main/docs/design/agentq-settings.md). Not a claim that remote management is shipped.

Local temporary controls ([agentq.md](../../agentq.md#temporary-controls)) add reversible detach/enable without broadening a grant. Disabled profiles block configuration with `integration_disabled`; project overrides block native-file edits. Revisions cover integration lifecycle and native/owned inputs. Retired routing, optimization and MCP request values remain parse-compatible but plans block unsupported operations and the executor defensively refuses retired writes with `feature_retired`; they never reactivate a removed feature. DashQ must remove their controls and render that refusal in its own stream.

## A1. Scope and ownership

Manage record hooks for Codex, Claude Code and Antigravity, and the Hermes record plugin. Claude Desktop Chat has no supported setup. Exclude login, model/provider, sandbox/approvals, foreign instructions, TaskQ admission and arbitrary commands. No compression recipe or engine is configurable.

Reuse discovery, ownership journal, lifecycle lock and existing apply/restore functions. Discover actual configuration roots locally; use stable opaque profile IDs without exporting paths. Clients sharing a configuration root are aliases of one target: display every affected alias in review, never promise isolation between them. Project overrides are reported read-only; conflicts with foreign providers/optimizers block affected writes.

Legacy `agentq direct` only restores owned routing, retaining the exact saved-chat direct definition. It is not an A3 setup operation. Unsupported fields are explicit, never off/zero.

## A2. Extended snapshot

Add an optional versioned profile-configuration projection to schema 1; retain unrelated identity, release, queue and resource fields; retired routing/engine/optimizer fields are omitted. Older producers have unknown configuration capability. Export only bounded typed fields:

- installation/runtime, source observation time, profile schema version and configuration revision;
- profiles: opaque ID, known client kind/aliases, sanitized owner-approved display label, supported operations and unavailable reasons;
- supported hook/plugin state and effective adapter/state; distinguish configured from verified;
- ownership/conflict flags and fixed reason codes, required client reload and affected target IDs; no raw config or free-text errors;
- per-profile verification: state, observed time, adapter, configuration revision and safe evidence ID, or unknown/reason. No verification inferred from config bytes or service liveness.

Revision covers the actual relevant settings and ownership/conflict state; it changes after out-of-band edits. Missing, stale and future/clock-uncertain observations remain unknown. Use § 5's 90-second status freshness, preserving source time through delivery. Cap profiles and strings, flag truncation/incomplete discovery and disable writes on incomplete targets. Do not export paths, prompts, logs, credentials, arbitrary instructions or model content. The sender reuses its existing queue/cadence.

## A3. Plan and guarded apply

One AgentQ-owned typed operation family plans/applies configuration for one installation and selected profile IDs. Allowed changes: explicit setup of supported owned record hooks/plugin. No caller-supplied file, executable, shell, provider, URL or engine pin. Discovery/setup cannot silently invoke legacy removal, uninstall, incident publication or unrelated service/configuration changes.

The host computes a bounded plan with old→new values, affected aliases, owned edits, conflicts, reload requirements and expected configuration revision. Browser review confirms that exact plan. An edit, different target or changed revision invalidates confirmation. The host re-reads settings under the lifecycle lock immediately before mutation, verifies target/capability/revision and preserves unrelated settings. A changed or stale plan is rejected with the draft retained.

Apply uses the existing ownership journal and crash-recoverable atomic writes. Persist one immutable operation ID, actor/target/plan digest and result outside the telemetry-pruned queue, bounded in the existing installation state. Duplicate deliveries return the same result; changed payload under the same ID is rejected. Interrupted/partial writes reconcile or restore owned values without overwriting later foreign edits; expose partial/unknown state, never a false success. Do not reapply an ambiguous operation blindly.

After apply, read actual configuration and effective record adapter state from the selected host. A matching readback makes it configured, not verified. A new real client turn through that profile/adapter must produce evidence correlated to the applied revision before verified. Required reload remains visible; do not fabricate activity or disrupt an active conversation to obtain proof. Verification failure preserves original output/client access and reports its cause.

## A4. Authorization and transport

Use the enrolled service's existing outbound HTTPS loop and DashQ's existing store for bounded typed requests/results; no listener, remote shell, extra daemon or second scheduler. Publish the operation envelope and conformance fixtures before the consumer adapter. Keep machine result delivery distinct from authority to request mutations.

Require a separately approved `agentq.configure` capability bound to actor/workspace, installation and profile scope; an observation credential cannot grant or broaden it. Reuse the authenticated consent boundary with explicit configuration effects. Revoke, expiry and destination/generation changes invalidate unapplied operations. The host accepts only authenticated operations for its active installation/generation and locally supported scope. Unenrolled standalone use remains unchanged.

Operations expire after five minutes unless execution began with valid authorization; offline expired operations never apply later. Persist accepted/result state for reconciliation; do not prune unresolved mutations or claim cancellation/revocation undoes an already committed change. Test both race orderings and return the actual outcome. Refuse acceptance if durable control storage is unavailable/full. Bound payload to 16 KiB and one outstanding mutation per installation; subsequent requests retain drafts. Errors and audit data use safe codes, actor/target/revision/operation IDs, never config contents or secrets.

### Operation envelopes

Schema 1, `agentq/configure.rs` (pure); shared conformance fixtures: [configuration-fixtures.json](configuration-fixtures.json), run by `cargo test` and `agentq selftest`. Every object is closed: an unknown key is `unknown_field`, so no file, command, provider, URL or engine pin can ride along.

- **Request** `{schema, operation, kind: plan|apply, actor, workspace, installation, generation, issued_at, expires_at, changes}`; apply adds `plan {revision, digest}` of the confirmed plan. `operation`: 32 lowercase hex, immutable. Actor, workspace, installation: opaque tokens, never paths. `changes`: 1–64 `{profile, field, value}`, one per profile and field: `hooks` `registered`, `plugin` `enabled`; old `routing` `routed|direct`, `optimization` `enabled|disabled`, `mcp` `registered` parse for compatibility but unsupported operations are blocked; retired executor writes return `feature_retired`; else `unsupported_field`/`unsupported_value`. No removal or uninstall value exists.
- **Acceptance order:** over 16 KiB `payload_too_large`; malformed `invalid`; a known operation returns its stored result when the canonical payload digest matches, else `payload_mismatch`; then `no_grant` (unenrolled or revoked), `observation_only` (any credential other than `agentq.configure`), `grant_expired`, `wrong_installation`, `stale_generation` (request or grant generation differs from the host's), `wrong_workspace`, `wrong_actor`, `profile_out_of_scope`, `invalid_expiry` (window over 300 s), `expired` (now ≥ `expires_at`, late offline delivery included). Apply then needs durable control storage (`storage_unavailable`), no other unresolved mutation (`busy`), the current configuration revision (`stale_revision`), a writable plan (`blocked`) and the same digest (`plan_changed`).
- **Plan** `{schema, kind: plan, operation, installation, generation, revision, expires_at, profiles, blocked, writable, digest}`; per profile `id`, `kind`, every `aliases` entry, `revision`, `changes [{field, old, new}]` in the projection's enums, `conflicts` (projection conflict and incomplete codes, `project_override`, `unsupported_client`, `unknown_profile`) and `reload` (record hooks or plugin changed). `blocked` unites the conflicts; `writable` only when empty. `digest`: SHA-256 of the key-sorted plan without operation and expiry, so any change to target, revision, value, alias, conflict or reload invalidates confirmation. A plan neither mutates nor reserves the installation.
- **Result** `{schema, kind: result, operation, outcome, reason, plan, profiles [{id, state}]}`. `rejected`: nothing changed, safe code. `accepted`: the host stored operation, actor, target and plan digest durably before any write; a lost receipt returns the same result. `applied`: readback matches, profiles `applied|unchanged`; configured, never verified. `partial`: some profiles `applied`, others `restored` or `unknown`, with a reason. `unknown`: interrupted or unread, with a reason; reconcile from the journal, never reapply blindly. Expiry, revocation or generation change after `accepted` reports the actual outcome, never an undo. Verification stays in the A2 projection.

### Host executor

`agentq/executor.rs` runs one request under the lifecycle lock (`data/lifecycle.lock`, also taken by `onboard` and `direct`): resolve interrupted operations, re-read profiles, `handle`, store the `accepted` record in `data/operations/<operation>.json`, write, read back, store the result. Resolved records keep at most 64, unresolved ones are never pruned. Writers reuse `onboard` wants and the ownership journal for record hooks and Hermes plugin source/activation. Unsupported clients block the plan. Setup checks the selected native CLI exists before any profile or journal write (`client_missing` when absent); presence is not login or turn verification. Hermes plugin preflights owned source before activation; foreign files block writes. Plans block retired operations as unsupported; the executor defensively returns `feature_retired` for retired writes. Its legacy direct restoration branch remains recovery-only.


Readback compares every changed field on a fresh profile read: all match `applied` (`unchanged` when already set); a mismatch restores this operation's owned journal entries and preference, then reads `restored` or `unknown`. Outcome: all applied `applied`; some `partial`; none and any unknown `unknown`; all restored `rejected` with the cause. An interrupted `accepted` record resolves from current state with reason `interrupted`, never reapplied.

Verification: `agentq hook <agent> <event>` stamps `data/evidence/<agent>.<event>`. A profile is `verified` when its revision still equals the one read back after its newest applied operation (ordered by a private monotonic journal sequence, with timestamp ordering for legacy records) and an event newer than that apply proves its effective state: a new `SessionStart` or `Stop` for a configured record-hook adapter. The plugin adapter has no verification source yet and stay unknown `no_evidence`; a later edit reads `revision_changed`. Each readback captures a private per-profile hook watermark at least as new as its apply time and every already recorded successful hook event. Verification needs an event strictly newer than that watermark; an older event with a future timestamp after clock rollback cannot verify a later apply. A legacy operation without a watermark stays `no_evidence` until a new apply and client event.

`agentq configure [<profile> <field>=<value>.. [--yes]]` is the local entry: no argument prints the profile projection, changes print the plan, `--yes` applies it. Its grant is local (actor and workspace `local`, generation 0, every current profile).

### Enrolled delivery

`agentq enroll` asks for `agentq.configure` beside the snapshot schema; the browser approves it separately and the host keeps only the granted subset (coreq wire v1 operations). Without it the service never pulls. With it, each 30 s service pass after snapshot delivery makes one `/operations` pull and runs each new operation through the host executor with the active grant's authority: its installation and generation, the workspace DashQ bound to it, and from the operation's server-set `authority` (coreq v0.11.0) the actor DashQ authenticated and the profiles that actor may change, plus the operation's expiry. Payload claims never add authority: a payload `actor` other than the authority's is `wrong_actor`, another `workspace` `wrong_workspace`, a profile outside its list `profile_out_of_scope`, a missing claim `invalid` (the request envelope requires it). Operations coreq rejects locally (`expired`, `digest_mismatch`, `scope`, `payload_too_large`, `authority` for a missing or malformed one, `workspace` for another workspace than the grant's) never run and get a `rejected` result with that reason; malformed, other-installation and other-generation ones get none. Revocation ends pulling at once.

The posted result is `{result, readback}`: the plan or result envelope and the A2 projection of the profiles it names (dropped when over 16 KiB). An accepted apply's operation record keeps the grant's actor and workspace. The result is stored with the authority's actor in `data/connection/results/<operation>.json` before posting, so a lost reply, a restart or a redelivery with the same digest posts it unchanged without running again; a different digest under the same ID is `payload_mismatch`. Posted results keep at most 64, unposted ones never prune. `agentq connection status` shows `configure` granted and the last pull or post error. Snapshot writes stay `not_released` until A5 qualification.

## A5. Qualification and release

1. Projection: old/new schema, missing/stale/partial/conflicting profiles, shared aliases and privacy leak fixtures; prove config revisions track external edits.
2. Host executor: supported/unsupported clients, exact diff, conflict/CAS rejection, scope isolation, duplicate/lost receipt, expiry/revoke, crash/partial rollback and effective readback. Existing local commands reuse the same authority.
3. Installed clients: configured vs verified, reload, real native turn, retired-integration cleanup and saved-chat direct access, original-output fallback, unchanged login/model/approvals and active work. Cover macOS, Linux, Windows and WSL where supported; Desktop Chat unsupported and Hermes record-plugin behavior are explicit.
4. End to end: actual browser grant, wrong workspace/profile, read-only device, host action and correlated fresh readback/evidence with exact AgentQ/DashQ versions. Restore the approved baseline after qualification. Test failure is a gap, never a simulated pass.

Release projection/read-only UI independently. Enable writes only after the typed contract, host qualification and consumer security gates pass. Prototype approval does not authorize changing installed profiles or deploying a candidate.
