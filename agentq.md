# agentq contract

agentq installs, routes and observes context optimization for Codex, Claude Code and Hermes on one host. This file holds every decision for the Rust rewrite on [coreq](https://github.com/taskqorg/coreq). It follows the [specq release contract](https://github.com/taskqorg/specq/blob/main/engineering/release-contract.md) and [taskq.md](https://github.com/taskqorg/taskq/blob/main/taskq.md) § 4 and § 8 as the reference consumer. Product outcomes stay in [docs/spec/PRODUCT.md](docs/spec/PRODUCT.md) revision 2; § 11 maps each requirement here.

Status: decisions for implementation. The legacy Node package `@alexkirs/agent-context` is gone from this repository; installed copies keep working until § 10 removes them on a host.

## Principles

- **Spec first.** A change that alters a decision edits this file first; code, README and INSTALL follow. Only the owner accepts a decision change. AGENTS.md points here.
- **One static binary.** `agentq`, built from an empty Rust codebase (PRODUCT R11). No Node, npm or toolchain on the host. Python only for the headroom engine (§ 3).
- **Client only.** The client holds no relay, GitHub App, gateway server, serviceq panel or dashboard. Server duties belong to [dashq](https://github.com/taskqorg/dashq) (§ 6, § 8).
- **Unverified means unknown.** Configured is not verified. Stale or missing values say so with a reason, never zero or success.
- **Never break the agent.** Any agentq failure keeps the original tool output and the client's own login, model, approvals and sandbox.

## 2. MCP tools

- Server name `agentq`; tools `index_document`, `search_document`, `get_original`. Tool names and input schemas stay stable (PRODUCT R2). The 0.9.0 namespace and managed instruction markers use the current name; clients reload registrations normally.
- `index_document`: UTF-8 file or text at most 1 MiB; stores the original and splits it into chunks.
- `search_document`: term-match ranking over chunks of one index; returns passages with their index ref. `ponytail:` plain term scoring in the binary; swap in an engine behind the same tools when a paired task test shows a gain.
- `get_original`: returns the retained bytes for a ref unchanged; an expired ref says `expired` and names the source.
- Limits: 100 originals per profile, 7 days, 256 MiB; oldest go first. context-mode is no longer an engine (§ 11).

## 3. Managed engines

Engine pins (version, per-platform URL, sha256) are built into the binary; no config changes them. An engine downloads into `<install>/engines/<name>-<ver>/` on install and on an update that changes its pin, is checked by sha256 and `--version`, and is never fetched by an install script.

- Engines install in `service install` before the unit loads and on each `service run` start, so a release with a new pin installs it; an engine already checked is reused. A failed engine never fails the command: its line names the reason and agents keep working without it.
- **RTK.** Prebuilt binary from `rtk-ai/rtk` releases, current pin 0.51.0. `agentq run` passes only commands on the built-in qualified list (`pytest`, `cargo test|build|check`, `go test`) to `rtk`; others run natively. Native RTK execution keeps command semantics; no generic post-filter. Raw output of each run is retained in `data/runs/<id>/` for `get_original` with ref `rtk:<id>` and the hash of RTK's recovery hint (500 runs, 7 days, 512 MiB). Read-only sandbox without writable storage or no checked RTK: run natively, no compression.
- **headroom.** Loopback model proxy for routing and usage observation; its request compression stays off; its supported extension sends qualified new tool results to the core below. Current pin `headroom-ai[proxy]` 0.40.0. Installed with `pip --require-hashes --only-binary :all:` from the lock `agentq/headroom.lock` built into the binary into a private venv `<install>/engines/headroom-<ver>/` from Python 3.11–3.13 found on the host (`AGENTQ_PYTHON` overrides); checked by `headroom --version`. The pin's wheels need macOS 14+ on arm64 and do not exist for macOS x64. No Python or no wheels: agents run unrouted, `doctor` says why. It never injects tools, never rewrites transmitted prefixes and never switches provider.
- Code, complete JSON, dense constraints and short results pass through (PRODUCT R3). Codex gets no compression hook; its adapter is the loopback provider.

### Tool-result compression

Accepted results target: [ACCOUNTING O1–O4](docs/spec/ACCOUNTING.md) defines outcome populations, paired byte measurements, coverage and whole-task evidence for PRODUCT R9/R10. This adds no optimizer, capture permission or universal savings claim.

One core in the binary decides, compresses, retains and counts; adapters only translate. A new agent needs an adapter, never a new core path.

- **Core.** Input: `agent`, `adapter` (`run`, `hook`, `provider`), `tool` (tool name), `command` (shell tools only; matched to a runner, never stored), `text`, native `exit_code` for captured results, native IDs when known. Steps: config off for the agent, under `min_bytes`, code or complete JSON: pass through (R3). Then only the built-in qualified list of that adapter selects an engine; anything off the list passes with reason `not_qualified`, so no generic post-filter. A result that is not smaller, an error or 3 s without an answer: the original text. A compressed result keeps the original under a `get_original` ref (`<engine>:<id>`, store and limits of `data/runs/`) and ends with one line naming that ref. Every call writes one stats record. Unqualified, disabled or unavailable-engine runs stay native without capturing output; their byte measurements are unknown. The run adapter captures eligible native stdout/stderr once before RTK filtering, keeps stderr and the native exit code, and returns native bytes whenever verification fails; its 3 s filter budget excludes native execution. A replay with changed arguments fails verification and returns the native capture. Retained originals are stdout bytes; stderr is never compressed.
- **Qualified lists.** Built into the binary, per adapter, changed only by a release; no config adds a tool. The runner set is the RTK list above.
  - `run` (Claude Code through its hook, any agent calling `agentq run`): a command whose runner is on the RTK list executes natively once; RTK executes a private replay of that capture through its qualified recipe, never the native command again.
  - `provider` (Codex `exec_command`, `shell`) and `hook` (Hermes `terminal`): the command already ran. Reuse the qualified run adapter's bounded RTK capture replay with the native exit code: RTK sees only the captured stdout/stderr and cannot rerun the native command. Replay verifies the native arguments and exit code; for pinned RTK pytest it also expects only its injected display flags (`--tb=short`, `-q`, `-rxX`, each omitted when the native args already set that category). A mismatch returns the original; native execution is never repeated. Recipes stay limited to the same runner set, with whole-task checks and the protected-result guards. Headroom keeps transport passthrough; its supported proxy extension calls this core, never its generic history optimizer.
  - Every other tool of every adapter (file reads, search, web, MCP results, other commands) passes unchanged.
- **Entries.** In process for `agentq run`; `agentq compress <agent>` reads one input as JSON on stdin and prints `{"text": .., "ref": ..}` for any agent with a result hook (input requires `adapter` (`hook` or `provider`), `tool`, `text`; optional `command` (string), `exit_code` (32-bit integer; required to transform a captured result), `session`, `turn`, `tool_call`); run identity comes from `AGENTQ_AGENT`, `AGENTQ_SESSION`, `AGENTQ_TURN`, `AGENTQ_TOOL_CALL` when supplied, else agent `unknown` and null IDs. The service calls the core for the loopback provider.
- **Config.** One section `compression` in `data/config.json`: `{"enabled": true, "min_bytes": 2048, "agents": {"<agent>": false}, "stats": "queue"}`; absent keys take these defaults. `stats` is the sink: `queue` sends each record through § 6, `off` keeps it local only.
- **Stats record.** One JSON object, same keys everywhere: `schema` (1), `event_id`, `time`, `agent`, `adapter`, `tool`, `runner` (or null), `engine` (`rtk`, `headroom`, `none`), `outcome` (`compressed`, `passed`, `failed`), `reason` (`compressed`, `disabled`, `short`, `code`, `json`, `not_qualified`, `not_smaller`, `no_engine`, `timeout`, `error`), `bytes_in`, `bytes_out`, `est_tokens_in`, `est_tokens_out` (labeled `estimate`, § 6; byte/token fields are null for unmeasured native passthrough, never zero), `duration_ms`, `ref`, `session`, `turn`, `tool_call`, `version` (agentq), `engine_version` (pin of `engine`, null for `none`), plus `exit_code` for `run`; readers treat a record without the last two as version unknown. Local copy: SQLite `data/telemetry.sqlite3`, kind `stats`, event ID unique, 7 days; legacy JSONL imports without deletion; `agentq stats [--json]` prints per agent and engine the call count, outcomes and bytes in and out. Sink `queue`: one `agentq.compress` span with each key as `agentq.<key>`; it replaces `agentq.run` when the core lands.
- **Accounting.** `agentq/accounting.rs` is one pure aggregate over these records or their exported spans, shared by `agentq stats --accounting` and the consumer fixtures `docs/spec/accounting-fixtures.json` (ACCOUNTING "Published schema"). Coverage is only what the producer proves: record and `meta.journal` (`since`, `resets`, legacy `gaps`, per-day `counts`) commit atomically. Missing/unreadable coverage over held records resets from the next second, rebuilding counts; its own second stays unproven. Failed transactions roll back both and leave `data/coverage.failed.*` outside SQLite until a later committed reset clears the markers it saw. Retention subtracts removed rows; pressure also advances `since`. Local totals always remain lower bounds: calls losing both record and marker are undetectable. Missing/corrupt stores, failed writes and fewer rows than journal counts read unknown, never zero. Legacy coverage gaps remain visible; exported events carry no completeness proof.

- **Adapter contract.** An adapter maps the native result to the core input, writes the returned text back in the native shape and keeps the original on any failure (Principles). It never holds thresholds, engine choice, retention, a retrieval tool, stats, telemetry, config or network calls of its own.
- **Claude Code:** outside native auto mode, the § 4 `PreToolUse` rewrite to `agentq run` is the adapter. In auto mode, keep the original command for native permission classification and compress only successful Bash stdout through `PostToolUse.updatedToolOutput`; stderr and the response envelope stay unchanged. Failed/interrupted/image results remain native because the failure hook cannot replace output. No hook grants permission or alters the client's mode.
- **Codex:** the loopback provider sends each new `function_call_output` or `custom_tool_call_output` (string, typed or JSON-wrapped text) of a listed tool through the core once per call ID, keeps the returned bytes per session and replays them on later requests, so the transmitted prefix stays byte-identical; other items pass unchanged. HTTP/SSE and WebSocket Responses use native `thread-id` (then `session-id`). Code mode qualifies only one literal `const|let name = await tools.exec_command({...}); text(name);` carrier; arbitrary JavaScript and multiple calls pass unchanged. Replay is durable in `data/provider/<session hash>.json`: 512 results / 16 MiB per session, 64 MiB total, no eviction of transmitted bytes. Corrupt, unwritable or full replay storage preserves the original.
- **Hermes:** the shipped plugin `agentq` registers `transform_tool_result` and `post_api_request` (model calls, § 6). `transform_tool_result` runs `agentq compress hermes` for `terminal`, the only Hermes tool on the core list, and unwraps its `output` field; other tools return before any call. No proxy URL, own retrieval tool, lifecycle call or query memory: retrieval is MCP `get_original`, as for every agent.

## 4. Hooks and config edits per runtime

### Temporary controls

- Compression and integration state are independent. Host optimization off writes `compression.enabled=false`; on writes `true`. Agent off writes `compression.agents.<agent>=false`; on removes that key. A host pause preserves agent preferences. All adapters and anonymous `agentq run` obey the host switch; per-agent isolation requires a known agent. Previously transmitted Codex replay bytes never change.
- A paused Claude hook leaves the native command and result unchanged. In auto mode, `PreToolUse` never adds the AgentQ wrapper; `PostToolUse` handles eligible successful results after native execution. The hook registration and MCP connection remain available. Older PreToolUse-only auto profiles need explicit hook configuration for successful-result compression; enable restores only their saved fields and does not silently add an absent PostToolUse registration.
- Full disable persists intent before removing owned routing, MCP, hooks, Hermes plugin files/activation and journaled instruction blocks. Keep the installation, release/engine assets, local data, originals, keys, grants and queued observations under their existing retention. Foreign entries and later edits remain; conflicts are explicit. Shared roots/registrations switch together. Only explicit `enable` clears disable intent; onboarding, service install/restart and configure cannot reconnect a disabled profile (`integration_disabled`). Manual binary update remains available without reactivation. `direct` keeps its existing routing-only meaning.
- Detach evaluates journal history against the simulated file after each receipt. Repeated legacy receipts for one owned registration are idempotent; later foreign values still block the whole affected file before writes.
- `data/integration.json` is bounded, versioned owner-only local lifecycle state under the existing lifecycle lock: generation, host-disable intent, saved service state and selected profiles with supported owned fields, transition stage and the journal metadata needed to recover an interrupted write. Record before writing; do not overwrite the first disable baseline on repetition. Resolved rollback metadata is discarded; unresolved transitions are retained. Missing state means no disable intent; corrupt/unreadable state means unknown and blocks mutations/new compression rather than resetting state. Never export its paths or values.
- Detach reuses scoped journal restore and forgets successfully restored active entries. Enable reuses current canonical wants filtered to the saved fields, retaining a prior Direct state, absent optional components and independent optimization preferences. It does not call onboarding, uninstall or legacy removal, replay obsolete registration bytes, or overwrite later foreign values. Prepare the existing proxy before restoring routed configuration. Partial writes reconcile by recorded stages and actual readback, preserving conflicts; ambiguous operations are not blindly reapplied.
- Codex conversations persist their provider ID. Removing owned Codex routing (`disable`, `direct`, uninstall) restores the native default selection but retains `agentq` as an exact, marked direct OpenAI definition, without a base URL or AgentQ dependency. Codex selects its native endpoint from the unchanged login/auth mode. This definition is not an attached optimization; enable/onboarding may replace only the exact unedited compatibility block with the current owned loopback definition. Later edits remain conflicts. Never rewrite conversation history, provider IDs in stored chats, authentication, model, approvals or sandbox to repair resume. Retain the independent direct definition after uninstall; previously detached installations can be repaired with the same definition when the name is absent.
- Hold the lifecycle lock only for durable intent/configuration/journal writes. Release it before client waits and OS service operations, then revalidate generation before finalizing. Dry-run writes nothing and previews selected aliases, changes, conflicts and reload impact. Explicit native configuration roots are authoritative; do not discover sibling installations or promise a switch for one worker.
- Detaching configuration does not unload a running client's cached provider/hooks/MCP. Suppress new transformations, preserve active work and expose `pending_reload`/`pending_drain`. No forced-stop option or elapsed-time proof: a conservative native process/session inventory must establish that dependencies ended/reloaded and proxied connections must read zero before stopping their transport. Unknown or unsupported inventory remains pending. A repeat finishes after dependencies clear; reload/reopen affected clients to use detached configuration. Never infer verified detach from removed hooks or TCP observations.
- While a host disable is pending, the existing service runs only required transport/recovery: export, automatic update activation and remote configuration application are suspended, except the enrolled DashQ snapshot (§ 5 `lifecycle` `pending_disable`), which keeps its 60 s cadence so DashQ can name the host disabled (#169). Langfuse events (heartbeat, resource samples, model calls), revoke retries and operations stay off. After a safe stop no second daemon or scheduler runs them. Per-agent disable preserves service for enabled siblings; a safely drained disabled proxy is not respawned. Save service registration/state for enable; honor disable intent after logon, reboot and service restart. Native login/model/approvals/sandbox and foreign telemetry settings are outside this operation.
- Service ownership requires the saved unit recipe and the executable/arguments of any live OS registration. An owned file cannot grant authority over a same-name registration loaded by another installation; unreadable registration evidence blocks service mutation.
- Status separates desired integration, observed configuration, runtime evidence and compression preference/effective reason. Claude's effective hook event is PostToolUse in auto mode and PreToolUse otherwise; runtime verification requires that event, and result-hook failures remain visible. The newest applied operation follows a private monotonic journal sequence under the lifecycle lock, so same-second writes or a wall-clock rollback cannot select an earlier revision; legacy records without a sequence retain timestamp ordering. Each applied readback also captures the latest existing hook timestamp as a verification watermark. Only a strictly newer event can verify it, including after a wall-clock rollback; legacy operations without that watermark stay unverified. Intent `disabled` with detached readback is not accidental routing drift in doctor. Local status does not turn a stale heartbeat into running/verified. Service status uses its own process, heartbeat and unit observations; an unknown client dependency inventory keeps profile runtime/drain unknown without invalidating independently observed running or intentionally stopped service state. Add only bounded optional lifecycle fields to snapshots; existing remote mutation envelopes and grants gain no disable/enable value.
- New/restored Desktop Chat MCP registrations use `agentq mcp claude-desktop` to distinguish its independent disable intent from Claude Code. Tool names and schemas stay unchanged. Existing shared `mcp claude` connections have no reliable caller identity and remain pending reload; do not disable Claude Code to guess their caller.
- Configuration revisions cover host `compression.enabled`, agent preference, its Direct membership, integration lifecycle intent and the existing owned/native inputs. Project overrides block fields editing native client files, not optimization-only changes to AgentQ preferences. Native qualification is reported per client and platform; code checks alone do not qualify working profiles. On 2026-10-17 the owner explicitly authorized the 0.8.0 rollout to the existing Mac, Windows and FRA installations with the Desktop/reboot gaps recorded in the integration-control plan. Those paths remain unqualified; this is not a stable-platform claim.

Accepted configuration target: [CONFIGURATION A1–A5](docs/spec/CONFIGURATION.md) owns extended profile projection and separately authorized typed management with revision checks, journaled apply, host readback and real-client verification. Observation enrollment grants no configuration authority; existing client/model/login/approval and ownership rules remain binding. Released in 0.6.0 before qualification #95. Typed request/plan/result envelopes and host acceptance: `agentq/configure.rs` with shared fixtures `docs/spec/configuration-fixtures.json`. Local guarded apply, readback and hook evidence: `agentq configure`, `agentq/executor.rs` (CONFIGURATION "Host executor"); remote operations ship in 0.6.0, unqualified.

Each edit is recorded in the ownership journal (§ 9) before it is written. Existing foreign optimizers or custom providers stop the edit for that file with a named conflict; nothing is replaced by guess. Loopback port per agent and runtime is fixed at install and kept across updates.

### Namespace cutover (0.9.0)

The current MCP server, Codex provider, managed instruction markers and Hermes plugin are named `agentq`. No old namespace alias is registered. The owner explicitly declined migration of existing Codex chats on 2026-10-17: histories stay intact, but chats bound to the retired provider must be replaced by new chats. New `agentq` conversations keep a direct OpenAI definition during disable so temporary controls do not repeat the missing-provider failure.

`agentq migrate-names [--dry-run]` updates only unchanged owned registrations and their journal/suspended receipts under the lifecycle lock; onboarding and service startup run it automatically. It preserves native login, model, permissions, sandbox, preferences, retained originals and queued data. It never resumes or edits a conversation. Clients reload normally; active workers are not killed. Only exact managed provider/instruction blocks, owned MCP keys and owned Hermes plugin files are renamed. Foreign edits or target-name collisions stop before writes.

The bounded owner-only `data/name-migration.json` retains the original ownership/control metadata for retry and rollback, without copying native configuration files. Native writes precede metadata activation; retry recognizes already-renamed values and files after an interrupted write. `agentq migrate-names --rollback` restores the recorded owned names only while ownership/control metadata still matches the cutover; later ownership/control metadata changes block rollback. Roll back names before selecting an older binary. Old-name literals remain only in migration/removal logic and historical evidence, not current registrations or aliases.

## 5. Install layout and service

coreq owns layout, update, launcher, rollback, service units and `status.json`; agentq passes tool name `agentq`, install folder and release repository `taskqorg/agentq`.

- Install: `~/.local/share/agentq`, Windows `%LOCALAPPDATA%\agentq`: `releases/<ver>/agentq`, `current`, `previous`, launcher `<install>/agentq`, `engines/`, `data/` (§ 8), `status.json`.
- Command registration: onboarding and `service install` make the stable launcher available as `agentq` for the installing user, without administrator rights. `agentq setup-path` repairs an existing install without changing integrations or restarting services. macOS/Linux use `~/.local/bin/agentq`, refuse a foreign file/link, and add an idempotent `~/.local/bin` PATH block to Bash/Zsh startup files (respecting `ZDOTDIR`). Windows adds the install directory to the user PATH without expanding or truncating existing entries, then broadcasts the environment change. New terminals load the change; existing processes keep their inherited PATH. Custom install roots still target their stable launcher.
- Command removal: uninstall removes only the Unix link whose target is this launcher's path, or this install directory's Windows user PATH entries. Shared Unix PATH blocks and other entries stay. Bash/Zsh are configured automatically; other Unix shells can add `~/.local/bin` themselves. Registration is per OS user, not a privileged machine-wide installation.
- Release: CI on a `v*` tag builds `agentq-<ver>-<os>-<arch>` for macOS arm64/x64, Windows x64, Linux x64/arm64 (static musl), plus `SHA256SUMS` and `latest.json`; a failing selftest publishes nothing. Each binary and `SHA256SUMS` carry a GitHub build provenance attestation (`gh attestation verify <file> --repo taskqorg/agentq`); installers and self-update check only the sha256. Trust is HTTPS plus who can push tags; the Node Ed25519 recipe signature and staged rollout are dropped (§ 11).
- Release line: 0.6.0 and later tags come from `main` (owner answer on #134), so enrollment and `configure` ship before qualification #95. The 0.5 line (0.5.7–0.5.9 from branch `release-0.5.7`, #116) ends.
- Engine safety: a checked Headroom venv is immutable; a failed version probe reports unavailable and never deletes it. Headroom checks, installation and proxy workers use one OpenBLAS/OMP thread.
- Service: one OS unit per host and runtime (coreq project `host`: `com.agentq.host`, `AgentQ-host`, `agentq-host.service`) runs `<install>/agentq service run` in `<install>`. It owns the loopback ports, headroom workers, OTLP intake, the queue sender, update checks and `status.json`. No other resident process.
- Single instance: a `service run` process is one whose command line runs a binary under `<install>/releases/` (the Windows launcher that supervises it is not counted). `service status` reports more than one as an error naming every pid. On Windows `schtasks /End` ends only the launcher, so `stop`, `uninstall` and `restart` end every such process tree, orphans included; `restart` ends the task first, starts the service only through the `AgentQ-host` task and succeeds only when exactly one `service run` remains and `status.json` names its pid within 90 s. `selftest` checks the count on a built-in Windows process list.
- `service install` copies the running binary to `releases/<ver>/` and to the launcher only where the bytes differ: Windows refuses to overwrite a running exe (os error 32). A running launcher of an older version that cannot be replaced stays and says so; it only reads `current`. `selftest` checks the skip against its own running binary and the BOM strip on a built-in fixture.
- Update: coreq steps, hourly; each update keeps only `current` and `previous` under `releases/`; a dashq release notice may trigger an early check. An engine pin change starts a new headroom worker on a new port, routes new connections to it, keeps open ones on the old worker, retires the old one after 15 min plus 30 s grace, then kills its process tree with an incident; at most two workers. A service run whose `current` names another release (its own hourly check or a CLI `agentq update`) restarts into it: it exits 75 on the first pass with no open proxied connection, at most 15 min after it saw the change, and the unit starts the new `current`. While connections stay open it logs the deferral and its count to the service log, once per change of reason; an unknown count defers like an open one. A service run not started by the launcher from `releases/<ver>/` never restarts itself.
- `status.json` lives at `<install>/status.json`, written every 30 s; `service status` treats it as unknown after 90 s. It adds to the coreq keys: `agents`, per agent with a config root its `routing` (routed, direct, bypassed, unknown) and `reason`, `intended` (`routed` for an agent with shipped routing, onboarded (an owned edit under its root) and not `agentq direct`; else `direct`) and `intended_reason` (`onboarded`, `routing not shipped`, `` `agentq direct` ``, `not onboarded`); `unknown` when `owned.json` (not a list of entries with a `file`) or `config.json` (not an object whose `direct` lists names) is unreadable or of another shape, never direct. Claude Code and Hermes are intended direct until their routing ships. `mcp`, `hooks`, `engines` (per engine its pin and `ready` or `unavailable`), queue `{pending, oldest_age, last_delivery, dropped}`, `model_backlog` (§ 6 Model calls), newest incident. `configuration` (CONFIGURATION A2, `agentq/profiles.rs`): per existing client root its kind, opaque `id`, `revision` (keyed hash of its files, owned journal entries, port and preference), routing, MCP, hooks, plugin, optimization, effective adapter/state, `owned`, read-only project `overrides` count (Codex `[profiles.*]`, Claude Code `.claude.json` projects with MCP servers or env; null when unknown or unsupported), `conflicts` and `incomplete` codes; no paths or file text.
- Compatibility N/N-1: data in `data/` changes only additively.

Follows the specq [host requirements](https://github.com/taskqorg/specq/blob/main/engineering/release-contract.md#host-requirements) rule (#172). agentq runs these external tools on a host. The managed engines RTK and headroom are pinned, installed and checked under § 3, not here.

| Tool | Minimum | Needed by | Platforms |
|---|---|---|---|
| `curl` | 7.55.1 | update and engine downloads, Langfuse export (§ 6), DashQ enrollment and delivery | all |
| `tar` | bsdtar 3.3.2 or GNU tar 1.29 | RTK unpack; Windows bsdtar also reads the RTK zip | all |
| Python | 3.11, below 3.14, with `venv` and `ensurepip` | headroom venv (§ 3), `check compression` | all except macOS x64 (no headroom wheels) |

| `security`, `secret-tool` (optional) | none | Langfuse key storage; when absent, the `data/langfuse` file (§ 6) | macOS, Linux |

- Minimums: curl 7.55.1 and bsdtar 3.3.2 are the copies Windows 10 1803 ships; every flag agentq and coreq pass is older (newest: curl `--proto`, 7.20.2). GNU tar 1.29 detects gzip on extraction. The Python range is the headroom pin's; `check compression` alone accepts 3.9+.
- Not host requirements: Codex, Claude Code and Hermes run agentq, not the reverse; their configuration compatibility is § 4, and `check compression` records their exact versions. Commands passed to `agentq run` belong to the user. `npm` runs only to remove the legacy package (§ 10), which brought its own npm. `gh` is not called: § 7 delivery is not wired into this binary yet and adds its row when it is.
- `doctor` checks each row. A versioned tool runs its version query; missing, unreadable or below its minimum fails as `host tool <name>: <found> below minimum <min>; <fix>`. OS components are checked for presence on PATH in one line. Optional tools report without failing.
- agentq installs only its engines and has no administrator rights. `service install`, `onboard` (with and without `--yes`) and each `service run` start (so each update) report every failing requirement with its fix step; `doctor` stays failed until the host provides it.
- A change that starts using a new tool, flag or API raises its row in the same change.
- Every agentq host tool call goes through one wrapper. A failed start, and a failed exit where success is required, is logged as `agentq: \`<command>\`: <error>` to stderr (the service log for `service run`) and returned as an error, never as an empty result. Exceptions: the run adapter keeps native stderr unchanged (§ 3), so its RTK failures stay stats outcome `failed`; the Python finder probes candidates and its error names every candidate tried; a read of the optional key store falls back to the file without a log line, while a failed write is logged. coreq's own calls (update, enrollment, service unit) follow coreq.

### DashQ release observation

The additive `release` object in `status.json`, snapshot schema 1 and the installation heartbeat (`agentq.release`, JSON) reports installation-scoped observation only. Existing installation identity and source `at` bind it to this producer; it grants no control authority.

- `selected`: CoreQ 0.11.0 `Tool::current()` reads `<install>/current`; only a bounded release identifier crosses. Missing, unreadable or invalid selection is null with `selection_unknown`.
- `running`: the producer binary's `Tool.version`; `coreq_version`: the Cargo.lock pin, 0.11.0. No dependency upgrade or capture integration is required.
- `health`: the running release's existing `releases/<version>/healthy` regular-file marker, consumed by CoreQ launcher rollback. A readable empty marker with a nonfuture modification time yields `state=verified`, `scope=status_written`, `version` and source `at`. This receipt proves that AgentQ wrote status, not routing, workload or client health. Missing, unreadable, nonempty or future markers remain unknown. It never verifies the selected version when that version differs from running.
- `lifecycle`: `waiting_for_activation` when selected differs from running (the existing § 5 drain rule still governs activation); `healthy` only for equal versions with this receipt; otherwise `starting` or `unknown`. Host disable intent yields `pending_disable`, unreadable lifecycle state yields `unknown`. No elapsed-time or socket-only detach proof is added.
- Snapshot and heartbeat reuse the status observation, allowlist fields and codes, and set current health/lifecycle unknown when its time is missing, future or older than 90 s. Historical versions and receipt time remain explicitly last-known. Older producers report `not_reported`. No paths, arbitrary errors or native configuration are exported.

## 6. Telemetry to Langfuse

- Target: Langfuse project `Agents` over OTLP HTTP JSON, `<host>/api/public/otel/v1/traces` with Basic auth. Native exporters (Codex observability plugin, Claude Code Langfuse env) send to the loopback OTLP port; agentq adds its own events and queues all of them. The Hermes Langfuse plugin keeps its own Langfuse host and keys and sends directly; agentq never edits its `.env` and adds no intake path for it (owner answer on #140).
- Standalone mode: `agentq langfuse` reads host, public key and secret key (three lines, secret without echo) and the queue posts straight to Langfuse. The host is `https://`, or `http://` on loopback only.
- Team mode: accepted [connection contract](docs/spec/ENROLLMENT.md) amends §§ 1/5/6/8. Coreq enrollment uses DashQ’s actual identity provider; its existing service sends allowlisted snapshots and eligible events. DashQ projection works without Langfuse; forwarding credentials stay server-side. Standalone behavior remains available.
- agentq events, one OTLP span each, span name = event name: `agentq.compress` (core result and run records, § 3), `agentq.retrieval` (one MCP tool call), `agentq.installation` (heartbeat of `status.json` fields at service start and hourly; the start heartbeat waits until no agent reads `unknown`, at most 5 min, so a proxy still binding (headroom takes about a minute) is not exported as an hour of `unknown` routing (#134); `agentq.routing` (#134) is the `status.json` `agents` object as a JSON string: per agent with a config root its `routing` (routed, direct, bypassed, unknown), `reason`, `intended` and `intended_reason`, `{}` when none; `agentq.routing_problems` lists `<agent> <routing> (<reason>)` for each agent intended routed but not routed and `<agent> intended unknown (<reason>)`, else `none`; `agentq.hooks` (#134) is a JSON array with one object per agent and event that has a record (§ 1 `hook`): `agent`, `event`, `state` of the latest run (`ok`, `failed`, `unknown` with `reason` `unreadable success stamp` or `unreadable failure record` when its success stamp, failure record or retained last failure is unreadable), `last_ok_at` (unix seconds or null) and `last_failure` (`{at, error}`, kept after a later success; null when it never failed); `agentq.hook_failures` lists `<agent> <event> (<error>)` for each hook whose latest run failed, else `none`; `agentq.model_backlog` (§ 6 Model calls)), `agentq.incident` (with § 7), `agentq.resource` (resource samples below), `agentq.model` (model calls below). Attributes on every event: `agentq.schema` (1), `agentq.event_id` (also the trace ID, so a resend is idempotent), time (span start), `agentq.stage`, `agentq.installation` (unique ID kept in `data/installation`), `host.name`, `agentq.runtime` (`macos`, `linux`, `wsl`, `windows`), `agentq.version`; engine versions, profile, agent and native session, turn and tool IDs when known, else `agentq.ids_unknown` with a reason. Metadata only: `agentq.compress` names only its tool and matched runner (`cargo test`, `go test`, `pytest`) and engine (`rtk`, `headroom` or `none`), never arguments; no raw content, keys or paths. Estimates carry an `estimate` label and never count as observed usage.
- dashq reads `agentq.*` observations for its Agents view in its own task; its current reads use the legacy Node names.
- Queue: one file per event under `data/queue/`, named `<unix seconds>-<event id>.json`; one sender thread in the service posts batches of at most 100 and deletes them after a standalone 2xx, or an explicit durable acceptance receipt when enrolled; caps 64 MiB and 7 days, enforced on each write and send; overflow drops oldest events and counts them in `dropped`. Writers never wait for the network: an outage, missing keys or an unwritable queue never blocks or fails agent work, and the queue drains on the next successful pass. `agentq telemetry status` prints pending, oldest age, last delivery, dropped and the last error; `verify` queues one `agentq.verify` event, sends now and reads its span back for 60 s through `GET <host>/api/public/v2/observations?traceId=<id>` (Langfuse v4 events-only servers answer 404 on `/api/public/traces`); a miss prints that query and its last answer (no observation: not ingested yet; 401: keys).
- Secrets live in OS protected storage (Keychain via `security`, Secret Service via `secret-tool`) or a 0600 file `data/langfuse` where neither tool works (Windows until a Credential Manager binding lands); never in config, argv, logs or telemetry. curl gets them through its stdin config.

### Model calls

Claude Code, Codex and Hermes model accounting for dashq (U3, U3b and U3c of dashq#177). `agentq.schema` 1, additive.

- Producer: the Claude `Stop` hook (§ 4) reads the session transcript at `transcript_path` and its `<session>/subagents/*.jsonl` from a per-transcript byte offset in `data/model/` (7 days), up to the last complete line. A rewritten or shorter file reads from the start. It shares the hook's failure record (§ 1 `hook`). A disabled Claude integration reads nothing. An existing installation gains the `Stop` registration through `onboard --yes`.
- Bounded passes (#161): a pass reads in batches of at most 512 lines or 4 MiB; each batch writes its spans in chunks of 32, one local SQLite transaction each, and one queue prune (one queue file per event, § 6 Queue), then saves its offset. A hook pass starts no batch and no chunk after 3 s, inside the 5 s hook budget; the offset then stops at the first line of the first call not written, so a pass never runs more than one chunk past its deadline. A pass's first chunk always runs, so every pass progresses. The offset file also records the bytes left. The service sender drains transcripts with bytes left on each pass (10 s per pass), so a session that ends mid-backlog still completes. `status.json` `model_backlog` and the heartbeat attribute `agentq.model_backlog` report `{state, transcripts, bytes}` (`pending` or `none`); an unreadable offset file reads `unknown` with a reason, never `none`.
- One call per native call ID: the Anthropic `requestId`, else the message `id`. Claude repeats a call once per content block; the last line of a call wins. Client-made `<synthetic>` messages are not calls.
- Span `agentq.model`, stage `call`, start = end = the line's source `timestamp` (hook time when unparseable). Event ID = first 32 hex of SHA-256 of `<installation>:model:<call id>`, so a duplicate counts once and a later reading of the same call (a correction, a lost offset) replaces it in the queue and in Langfuse. A call without a native ID keys on its transcript line.
- Attributes besides the common ones: `agentq.agent` (`claude`), `agentq.session`, `agentq.model.source` (`claude_transcript`), `agentq.model.name`, `agentq.model.call_id`, `agentq.model.input_tokens`, `agentq.model.output_tokens`, `agentq.model.cache_read_tokens`, `agentq.model.cache_creation_tokens` (the transcript's `usage` integers).
- Cost: only a cost the client reports (`costUSD` on the line) gives `agentq.model.cost` (double), `agentq.model.cost_currency` (`USD`) and `agentq.model.cost_source` (`claude_transcript`). Current Claude Code reports none: `agentq.model.cost_unknown` is `not reported`. agentq computes no price; estimates belong to dashq with their own source.
- Unknown is never zero: a missing field omits its attribute and sets `agentq.model.<field>_unknown` to `not in transcript`. The span is a Langfuse `SPAN`, not a `GENERATION`, so Langfuse infers no price.
- Hermes (#163): the plugin's `post_api_request` hook runs `agentq hook hermes post_api_request` once per provider call with only `api_request_id`, `session_id`, `turn_id`, `model`, `response_model`, `ended_at` and Hermes's normalized `usage` buckets; request, response and message content never leave the plugin. One `agentq.model` span per call, same event ID rule with call ID `api_request_id` (a call without it keys on session, turn and end time), start = end = `ended_at`. Attributes as above with `agentq.agent` `hermes`, `agentq.model.source` `hermes_hook`, `agentq.turn`, name `response_model` else `model`, `cache_creation_tokens` from `cache_write_tokens`; a missing value reads `<field>_unknown` `not reported`. Hermes reports no cost in this hook: `agentq.model.cost_unknown` is `not reported`. A disabled Hermes integration has no plugin and reads nothing; an existing installation gains the hook through `onboard --yes`, which upgrades an owned plugin file whose bytes still equal its journal record (journal first) and keeps any other content a conflict.
- Privacy: model name, IDs and integers only; no prompt, output, tool input or path.
- Codex (U3b): the loopback provider (§ 3 Codex) reads each `response.completed`, `response.incomplete` or `response.failed` event (SSE, WebSocket or a plain JSON response) it already parses and passes only the response `id`, `model`, `usage`, `created_at` and the native session to `agentq model codex` in a background thread; the stream stays byte-identical and a failure only logs. A disabled Codex integration queues nothing. Call ID = the response `id`; the span is the same `agentq.model` with `agentq.agent` `codex`, `agentq.model.source` `codex_provider` and event ID from the call ID, so a resend or a later reading of the same response replaces it. Start = end = `created_at` (entry time when absent). Tokens keep the Claude meaning: `input_tokens` is uncached input (`usage.input_tokens` − `input_tokens_details.cached_tokens`), `cache_read_tokens` is `cached_tokens`, `output_tokens` is `usage.output_tokens` (reasoning included). The Responses API reports no cache creation and no cost: `cache_creation_tokens_unknown` and `cost_unknown` are `not reported`; any other missing field reads `not in response`. A response without `id` keys on a hash of its entry.

### Resource samples

Contract for dashq, `agentq.schema` 1, additive: consumers that ignore unknown span names keep working.

- Producer: the service's telemetry sender (§ 5), so one sampler per installation, on Linux, macOS, Windows and WSL. Native Windows and WSL are separate installations with their own `agentq.runtime` (§ 4) and describe different scopes: `windows` is the whole host, `wsl` is the WSL 2 VM, whose CPU, memory and virtual disk the Windows host already counts inside its own numbers. Consumers never add a `wsl` installation to the `windows` one on the same `host.name`. WSL uses the Linux probes and excludes Windows drives (`drvfs`, `9p`), so no filesystem is counted twice. WSL 1 (kernel release containing `Microsoft`) has no VM: its `/proc` mirrors the Windows host, so CPU and memory are unknown with `wsl1 mirrors the Windows host`, and its `lxfs`/`wslfs` root is not a local filesystem. Standalone samples use Langfuse. Enrolled samples use the same queue and DashQ durable ingestion/history; no additional sampler, local queue or client database.
- Cadence: one sample per 300 s wall-clock bucket `floor(unix / 300)`, taken by the first sender pass (30 s pace) in a bucket; a service start waits for the next bucket. Event ID = first 32 hex of SHA-256 of `<installation>:resource:<bucket>`: a resend, a second sampler or a clock step back into a used bucket replaces that trace, never adds one; the queue keeps one file per ID.
- Span `agentq.resource`, stage `sample`, start = end = wall time of the reads (source timestamp). Besides the common attributes:
  - `agentq.resource.cpu_percent` (double, 0–100, step 0.1): busy share of all CPUs over the interval since the previous read in this service run; `agentq.resource.cpu_interval_ms` (int) is its monotonic length. Linux `/proc/stat`: busy = user + nice + system + irq + softirq + steal of total = busy + idle + iowait (guest is inside user). macOS `HOST_CPU_LOAD_INFO`: busy = user + system + nice of total = busy + idle. Windows `GetSystemTimes`: busy = kernel − idle + user of total = kernel + user (kernel time includes idle).
  - `agentq.resource.memory_total_bytes`, `memory_available_bytes`, `memory_used_bytes` (int bytes, used = total − available). Linux `/proc/meminfo` `MemTotal`, `MemAvailable`. macOS `hw.memsize`; used = (internal − purgeable + wired + compressor) pages × page size, Activity Monitor's Memory Used. Windows `GlobalMemoryStatusEx` `ullTotalPhys`, `ullAvailPhys` (Task Manager's In use = total − available).
  - `agentq.resource.disks` (string: JSON array, one object per filesystem): `id`, `role` (`root` for `/` or the Windows system drive, else `other`), `fstype`, `used_bytes`, `free_bytes`, `total_bytes`: total = blocks × block size, free = blocks available to unprivileged users, used = total − all free blocks; reserved blocks make used + free < total. Linux matches `df`; macOS APFS counts the whole container (Finder, `diskutil apfs list`), where `df` Used shows only the volume. A filesystem whose stat fails has null numbers and `unknown` with the reason.
- Unknown is never zero: a failed, denied or missing probe omits its numbers and sets `agentq.resource.cpu_unknown`, `memory_unknown` or `disk_unknown` to a short reason. CPU: the service reads a baseline at start, no state survives a restart; an interval under 10 s gives `warmup`; counters that went backwards (32-bit macOS tick wrap) give `counter reset`.
- Filesystems are re-read on every sample; a mount change adds or drops an entry in the next one, never a zero. Linux reads `/proc/self/mountinfo` and keeps local block filesystems (`ext2`, `ext3`, `ext4`, `xfs`, `btrfs`, `f2fs`, `zfs`, `bcachefs`, `jfs`, `vfat`, `exfat`, `ntfs3`), one per device number, the shortest mount point first (bind mounts, btrfs subvolumes); pseudo (`proc`, `sysfs`, `tmpfs`, `overlay`, `squashfs`, ...), network and FUSE filesystems are excluded. macOS keeps `getfsstat` mounts flagged `MNT_LOCAL` without `MNT_DONTBROWSE`: `/` (its APFS container) and browsable external volumes. Windows keeps drive letters of type `DRIVE_FIXED` (`GetLogicalDriveStringsW`, `GetDriveTypeW`), fstype from `GetVolumeInformationW` (`unknown` when it fails, e.g. a locked BitLocker volume), numbers from `GetDiskFreeSpaceExW`: free = available to the caller, used = total − total free; removable, network, optical and RAM drives and folder mounts are excluded. WSL 2's `/` is its virtual disk: total is the disk's maximum size, while the Windows drive that holds it bounds real free space.
- Identity and privacy: `agentq.installation` names the install; a filesystem `id` is the first 16 hex of HMAC-SHA-256 over mount point and fstype, keyed with `data/resource-key` (32 random bytes, never exported): stable while the mount stays, not reversible to a path. No mount path, device or volume name, username, process or command output is exported.
- Clocks: bucket and timestamp use the wall clock, intervals the monotonic clock. When wall and monotonic deltas differ by over 2 s (clock step, suspend), `agentq.resource.clock_step_ms` holds wall − monotonic.
- Freshness and window: dashq shows the newest sample as stale after 900 s (three buckets) and draws a graph only from three or more samples, else says too few samples. A query spans at most 7 days (the queue cap); older history lasts as long as the Langfuse project retains traces. An outage delays samples within the queue caps; they arrive with their source timestamps.
- Overhead: a sample is a few file reads or syscalls and one span of about 1 KiB: 288 spans per host per day; a test bounds one sample at 50 ms.

### Profiling

Follows [specq profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md). Reuses the § 3 stats records and the queue `state.json`; no second collector, process or network call.

| Operation | Sample | p95 budget | Failure budget |
|---|---|---|---|
| `compress.run` | § 3 stats record, adapter `run` | none: `duration_ms` includes the native command; the 3 s filter budget is enforced inline | 1 % |
| `compress.hook`, `compress.provider` | § 3 stats record of that adapter | 1000 ms | 1 % |
| `export.langfuse` | one per send pass that posted or failed (§ 6 Queue) | 10 s | 5 % |
| `export.dashq` | one per delivery of grant-bound records (ENROLLMENT) | 10 s | 5 % |
| `proxy.request` | none: the headroom proxy serves model requests, agentq records none | unknown | unknown |

- Counters: always on. A stats record is the compression sample: outcome `failed` is a failure and its `reason` the error class. An export sample is `time`, operation, `duration_ms`, `class` in SQLite kind `export`, last 256 per operation; legacy state snapshots import without deduplicating equal observations; class null on success, else `auth`, `http`, `timeout`, `network`, `queue` (Langfuse) or `no_reply`, `stopped`, `rejected` (DashQ).
- Traces: `agentq profile trace on [<minutes>]` sets `profile.trace_until` in `config.json`, default 15, at most 60 minutes; `off` removes it. While on, `compress.run` writes its `native` and `filter` steps and each export its posted batches to SQLite kind `trace`: `time`, `op`, `step`, `duration_ms`, `class`. Kept 7 days; a day stops at 1 MiB of canonical payload; legacy JSONL stays readable through import. `agentq profile` reports the switch state.
- Store: operation names, numbers and class codes only; no secrets, arguments, content or paths.
- Report: `agentq profile [--json]` over the 7 days up to the report time, later timestamps excluded: per operation its calls, failure rate and classes, p50/p95/max ms (nearest rank), mean, standard deviation and its coefficient of variation `cv`. Over budget: p95 above its budget (`time`), failure rate above its budget (`failures`), `cv` above 1 (`unstable`). Rank: the largest of p95/budget, failure rate/budget and `cv`, worst first; unknown operations last. Trace lines add per-step calls and p95.
- Unknown: no samples in the window, an unreadable stats record (all `compress.*` operations) an unreadable or non-object export state or `profile` value (all `export.*` operations) or a malformed sample list or sample (that operation only) reads unknown with the reason, never zero or ok; the other operations still report. An unreadable `config.json` or invalid `profile.trace_until` makes the switch unknown, never off, and writes no trace; an unreadable trace directory, file or line makes the steps unknown.

## 7. Incidents via coreq

- coreq incident reports, option A: an issue in `taskqorg/agentq`, label `incident`, through the user's existing github.com login; dedup by fingerprint; no relay and no GitHub App.
- Only faults of the built-in catalog report: engine start, update, routing, queue overflow, worker kill. Payload is coreq's allowlist JSON, at most 4 KiB, enumerated values only.
- No login, offline or unknown delivery: kept in `data/incidents/<fingerprint>.json` for manual submission. Opt-out: `incident_reports = false` in `config.json` or env `AGENTQ_INCIDENT_REPORTS=off`; setup discloses destination, visibility and account before any send.
- A report never changes agent work or an exit code.

## 8. State

`<install>/data/`: `owned.json` (ownership journal), `config.json` (incident opt-out, mode, ports, `direct`, `compression`, `profile`), `installation`, `resource-key` (§ 6), `langfuse` (fallback only, § 6), `originals/`, `runs/`, `provider/` (durable transmitted-result replay, § 3), `model/` (transcript read offsets, § 6 Model calls), `stats/` and `traces/` (legacy history), `queue/` (delivery files and `state.json`: last delivery/error/dropped; old export samples preserved), `incidents/`. Local telemetry uses `telemetry.sqlite3` (SQLite/WAL, FULL, 2 s busy timeout, 64 MiB including sidecars); stats/traces retain 7 days, exports 256 samples per operation. Preserve event IDs, atomic coverage, legacy history and optional export. `stats --records` exports retained metadata for local qualification. Existing OTLP events also persist locally before optional delivery; compression uses its canonical stats row. `telemetry export` emits versioned metadata-only JSONL with errors and unknown completeness. JSONL remains the legacy format. Other state stays plain files with atomic rename and one lifecycle lock. Interrupted transactions resume or roll back from the journal on next start.

Dashboard duties (fleet view, versions, last seen, health, usage, incidents, access control) move to dashq, which reads optional Langfuse events and authenticated snapshots under the accepted connection contract. agentq ships no panel and no dashboard JSON.

## 9. Ownership and uninstall

- The journal records each created or reused component and each edit (file, key path, before value, after value) before mutation.
- `uninstall --dry-run` prints every restore and removal. `uninstall` restores owned values whose current value still equals the recorded after value, keeps later foreign edits and reports conflicts, stops and removes the service unit, engines, data and install folder. Logins, shared keys, reused components, exported history and the dependency-free Codex provider direct definition (§ 4) stay. A second run says `already removed`.

## 10. Legacy Node install

- `onboard` detects `~/.agent-context` and the global npm package `@alexkirs/agent-context`. The install is `<legacy>/launcher.mjs`: a folder without it (a still-running legacy process recreates `incidents/` and `machine-id.json`) counts as removed, as does a folder with `<legacy>/.retired`. `onboard`, `doctor` and `uninstall --legacy` name the pids of processes whose command line holds `<legacy>/` (Windows: `<legacy>\`, case-insensitive, read from `Win32_Process`).
- `uninstall --legacy [--dry-run]` removes the legacy install without Node; `<legacy>` is `$AGENT_CONTEXT_HOME/.agent-context`, else `~/.agent-context`, and its parent is the home of the configs it edited. The Node journals (`<legacy>/backups/*/journal.json`) give the file list only, limited to the known Codex, Claude Code and Hermes files: a user edit made after the journal never blocks.
  - Each listed file is copied to `<legacy>/config-backup/` (a rerun keeps the first copy), then only legacy entries are stripped: hooks and MCP servers that name `launcher.mjs` or `agent-context`, env values routed to the legacy proxy ports, Codex `model_provider = "agent_context"` and `[model_providers.agent_context]`, Hermes `supercompress` and `agent-context` plugin entries, instruction marker blocks. The Hermes `plugins/agent-context` files are removed.
  - The `contextq-monitor` launch agent, Windows task or systemd unit is unloaded, the global npm package `@alexkirs/agent-context` removed, and `<legacy>` moved to `<legacy>.retired-<YYYY-MM-DD>`, so the backup ends in its `config-backup/`. Running legacy proxy pids are listed and left for the user.
  - When the move fails (Windows: running proxies hold files, access denied), the folder is copied to the retired path, each copied file and emptied folder is removed where it can be, `<legacy>/.retired` names the retired path, and the remaining files are listed as locked; the removal succeeds. `doctor` lists those files and the legacy pids until the user stops the processes and deletes `<legacy>`.
- `onboard --yes` with a legacy install runs `uninstall --legacy` without a prompt (`--yes` is the consent), then applies § 4. A failure stops onboarding with its message.
- Retired names remain recognized only for removal and the one-time namespace cutover (§ 4). Current registrations use `agentq`; existing relay-filed issues and Langfuse traces stay.
- The relay worker and its GitHub App are retired: the code is gone from this repository, the owner deletes the deployed Worker and the App. Node clients that still default to the relay keep reports in their local queue.
- Final npm version: `npm-final/` is the package `@alexkirs/agent-context` 0.5.0; every invocation prints the migration instruction to stderr and exits 1, nothing else, no install scripts. The owner publishes it as a release asset without `recipe.json`, so the legacy updater never selects it and `uninstall --legacy` keeps working.
- The Node code, gateway, its tests, benchmarks, Python adapters and recipe signing are removed from this repository; only `npm-final/` stays. Manual removal on a host without agentq: `node ~/.agent-context/launcher.mjs uninstall --dry-run`, then `uninstall`.
